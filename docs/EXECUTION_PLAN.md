## 0. 论文（Thesis）

> **用 SPY×FAMILY 十分钟体验，证明一个命题：用户能进入一个世界、采取行动，而世界以「真实的、持久的、按视角过滤的」后果回应。**

成功判据不是"架构文档完整"，而是**一个可运行、可被用户验证的体验闭环**。本计划是**集成主导**，不是理论主导。

**版本档位（V1.1 已定案，进取路线）：** 完整数据驱动内核（X2）+ LLM 提议为主通道（X3）+ 代理循环提前引入（X4）。这意味着本月同时推进内核、LLM、代理三层——**高风险、高回报**。为此本计划内建三个对冲：① 确定性底线（测试与离线走查始终可跑，LLM 永不硬阻塞体验）；② 阶段性"部分学分"门槛（即使代理循环滑期，体验仍有可运行形态）；③ 每周日全局再推导（防过拟合）。

**全局判断（防过拟合的出发点）：** 架构理论已收敛且单元级验证通过（P0 切片 21/21）。真正的瓶颈是**鸿沟**——"孤立可用的内核"与"用户可感受的体验"之间的集成断层。所有工作必须回答：*这一步让用户更接近「进入一个活世界」的哪个瞬间？* 答不上来的，不做。

## 1. 全局再推导（从愿景出发，不是从文档清单出发）

### 1.1 愿景 → 本月的落点

```
愿景 North Star: Make imagination executable
  → 本月要证明的最小闭环: 想象 → 世界出现 → 进入 → 行动 → 世界真实回应 → 界面随视角变化
  → 具体验证载体: 10_MINUTE_EXPERIENCE.md 的 10 步脚本
  → 核心承诺(按优先级): 信息不对称 > 可感知后果 > 场景化界面 > 持久世界 > 自治 NPC
```

### 1.2 关键洞察（为什么不是"照做 MONTH_1_PLAN"）

审计后最尖锐的事实（已核实代码）：

1. **P0 内核是硬编码的。** `src/world/runtime/kernel.ts` 中 `speech_act` 分支硬编码实体 ID `char:p0:yor_forger` 与关系 ID `rel:p0:loid_yor_marriage`，Yor 反应也是硬编码模板。
2. **表示层有一个 43KB 的完整 SPY×FAMILY 定义**（`src/world/representation/examples/spyFamily.ts`），但**当前内核无法驱动它**——ID 不匹配，规则不是数据驱动。
3. **十分钟脚本需要 ~8-10 个角色、4+ 个地点**，而 p0 世界只有 3 角色/2 地点，**不足**。
4. 因此，本月核心工作是**三个并行必要动作**：
   - **A. 完整数据驱动内核**（X2）：内核完全由 `WorldActionDefinition` 驱动，对齐 Architecture Zero §8——前提 7/7、效果/级联/观察全部数据驱动。
   - **B. 编写最小 SPY×FAMILY 定义**：一份"够用即可"、匹配 10 步脚本的角色/地点/秘密/规则定义（而非照搬 43KB 完整版）。
   - **C. LLM 提议为主通道（X3）+ 代理循环（X4）**：意图解析与 NPC 对话以 LLM 为第一提议者，内核校验提交；NPC 从模板反应升级为"感知→决策→候选事件"的真代理循环。

> **一句话抓住本月**：*把硬编码内核升级为完整数据驱动、以 LLM 提议为决策通道、并让 NPC 成为有独立视角的代理，端到端驱动一份最小 SPY×FAMILY 定义，跑通十分钟体验。*

### 1.3 LLM 优先与确定性的关系（架构完整性红线）

"LLM 优先"不意味着"LLM 必须"。Architecture Zero 的两条不变量在此强制成立：

1. **LLM 只提议，内核只写入**——LLM 输出经内核校验后才以"已记录输入"进入事件日志（ADR-008）。
2. **记录输入决定论**——测试与离线走查使用确定性解析器或记录好的 LLM 输出固件，重放与断言不受 LLM 随机性影响。

因此 LLM 通道是**第一提议者**，确定性解析器是**测试/离线路径 + LLM 不可用时的自动回退**。两者共享同一 `resolveUserAction → candidate event → validate → applyEvent` 接口。这条红线保证：即使本月 LLM 层不完美，体验永不硬阻塞。

## 7. 质量门禁与提交仪式（用户规则，强制）

1. **每次提交前**：`npm run lint`（tsc --noEmit）+ `npm run test` **必须全绿**；否则不得提交。
2. **每次提交前**：向用户提出 **2-4 个校准定位问题**，确认当前阶段方向未漂移后再提交（与第 1 条并行执行）。
3. **每项改动**必须标注：*用户可感知效果 + 验证方法*；无法标注验证的改动不做（MONTH_1_PLAN 纪律）。
4. **LLM 测试纪律**：LLM 通道的功能测试使用确定性固件（记录好的 LLM 输出）或确定性解析器；不依赖真实 API 的随机性，保证 `npm run test` 稳定可重放。
5. **删除纪律**：任何模块在替换品存在且测试通过前不得删除（ARCHITECTURE_MIGRATION 规则）。
6. **每阶段退出门**未达成，周一/当日优先补，不跳过、不掩盖。
